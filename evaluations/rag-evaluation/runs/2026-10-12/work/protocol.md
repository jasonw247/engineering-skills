# Synthetic fixture evaluation protocol (declared before execution)

Mode: run. Decision: establish deterministic behavior of both supplied variants on the three supplied cases and locate changes in their observable outputs. This is a functionality exercise, not a production benchmark, release gate, or generalization study.

Inputs are `fixture_system.py`, `queries.json`, and `corpus.json`, unchanged. Run `fixture_system.run(query, corpus, variant)` once for each paired query and each variant with one process and no external calls. The implementation is deterministic; repeated draws add no independent evidence. Preserve raw outputs and exceptions. Record hashes, runner version, environment, run timing, and before/after input hashes.

Use the supplied `answerable`, `expected_mpa`, and `sufficient_sets` as the fixture rubric. These are supplied labels, not newly human-reviewed production labels. There is one requested factual claim per answered query: the maximum pressure in MPa applicable to the specified entity, revision, and temperature. Accept any alternative sufficient set, including `exception-copy` alone for the hot query. Do not require the general rule alongside a self-contained exception. The two exception records represent alternative wording of the same procedure section, not independent corroboration. The ordinary query's supplied sufficient set is `general`; this acceptance is specific to this fixture rubric.

Before declaring support, check that each used source exists and matches the query entity and revision; the fixture has no access labels. For this closed fixture, sufficient evidence means that an entire supplied alternative source set is present within applicable delivered evidence. Support for the emitted pressure additionally requires that the value matches the supplied applicable pressure. A cited ID's existence alone is insufficient. Unexpected sources without a reviewed rubric would need adjudication, not an automatic semantic wrong label; this run is confined to the supplied closed corpus and labels. A changed corpus or schema must trigger rubric review.

Scored units and denominators:

- Candidate complete-evidence rate: answerable cases with an entire alternative sufficient set in the returned candidate list / all supplied answerable cases. It describes candidate availability, not what the reader inspected; no cutoff other than the full returned list.
- Delivered complete-evidence rate: answerable cases with an entire alternative sufficient set in delivered applicable evidence / all supplied answerable cases.
- Answerable correctness/completeness: answerable cases with the requested correct pressure and no abstention / all supplied answerable cases. One required fact per case. Score separately from evidence sufficiency.
- Overall task correctness: all cases with the correct answer when answerable, or explicit abstention with no pressure when unanswerable / all three cases.
- Supported-claim rate: emitted pressure claims supported by delivered applicable evidence / emitted pressure claims. Citation support uses attached citations that were also delivered, with the same applicability/value rubric. Citation coverage counts claims with at least one citation / emitted claims. Source existence is diagnostic only.
- Unanswerable abstention: unanswerable cases explicitly abstaining with no pressure / all supplied unanswerable cases. Answered fraction: cases emitting a pressure / all cases.
- Scope violations: delivered records mismatching entity or revision / delivered records. Record any evidence outside the returned candidate list separately.
- Failures: exceptions or malformed outputs stay in the case population, count as unsuccessful task completion and failed evidence/correctness on answerable cases, and are not relabeled abstentions. They emit no scored factual claims. Empty claim denominators are not applicable, never perfect support. A timeout is a failure if encountered; no hard timeout is required for this inspected terminating local fixture.

Controls: identical corpus, cases, code snapshot, execution environment, and interface. Both variants return at most one evidence record. Their selection and unsupported-query behavior change together, so this is a bundled variant comparison; do not attribute the entire gain to a reranker, retrieval improvement, or parent expansion. No model, embedding, index, parser, generated summary, or explicit token budget exists in the fixture.

Report paired case changes and aggregate numerator/denominator counts without inferential confidence intervals: three hand-authored related cases are neither an independent deployment sample nor a held-out confirmation set. Do not tune the implementation. A promotion rule, minimum useful gain, and operating ceilings would need workload-specific agreement and representative reviewed confirmation data. Function timings, if recorded, are measured local diagnostic timings only. Production latency, tokens, build/refresh work, throughput, and monetary cost are not measured here.
